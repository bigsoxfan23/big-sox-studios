## Architecture and immutable intake

`membership-notify/wrangler.toml` defines a separate Worker, with no routes, domain, workers.dev, previews, assets, service bindings, or Mail Desk bindings. HTTP always returns 404. Its only database is the existing, newly isolated membership database `bss-membership-requests`, UUID `21e13fa1-0ab3-4573-8d20-983c847ba0e9`. This is not Mail Desk's database. The proposed five-minute cron is the third known trigger (public retention and Mail Desk are the other two), within the stated Free maximum of five; current account plan, inventory, quota and $0 headroom still require verification. This run does not create another database or Worker.

Migration `membership/migrations/0002_notifications.sql` is additive to version 1. A genuinely new application insert transactionally creates one durable minimal case record and one uniquely keyed `submitted` outbox event via SQLite triggers. Any outbox/audit failure rolls back the application insert. Public validation, mandatory Turnstile verification for every submission (including duplicates), response text and status, and `ON CONFLICT(email_hash) DO NOTHING` are unchanged. Duplicate intake cannot update applicant identity, enqueue another event, or send another notification. No provider dependency or secret enters the public Worker. There is no service endpoint, signature or shared transport secret because this architecture communicates exclusively through the isolated D1 outbox.

Immutable event identity comprises application UUID, event kind, revision and occurrence timestamp, protected by a trigger. Case identity, original creation timestamp and retroactive-mail suppression are also immutable. Strict unique indexes prevent a second submission/adoption event and duplicate review revisions. Events contain no name, email, reason, note, fingerprint, IP, token, or message content. Applicant records remain the source of private review data; no second PII snapshot is created.

Actual status changes enqueue a separate deduplicated `status` event, including retention expiration. Note-only updates and PII clearing do not enqueue. Legacy applications changed by the owner can sync decisions but have permanent email suppression. Review jobs read the latest source status, reconcile the page, and PATCH `Status` and `Membership Decision`; they never send mail or change ownership, Reference or Sequence, create accounts, or invite applicants. Existing owner revision/CSRF/auth rules are unchanged.

## Processing and provider safety

The new Worker is entirely disabled by default. `NOTIFY_ENABLED`, `NOTION_ENABLED`, and `EMAIL_ENABLED` are the literal string `false`. Missing flags never enable anything. Completed deidentified events are pruned in batches of 100 at 365 days before enablement/provider checks, including with missing/false flags or unavailable Notion. Disabled invocations perform only this bounded database housekeeping and never contact providers or dispatch. Migration `0003_notification_provider_check.sql` adds an index on event state/age/ID and one persistent provider-check budget row; it preserves all existing application, event and effect state. Enabled processing requires schema version 3. At most one due pending event is read per invocation, ordered by due time then event ID; no due work means no provider request. Exact required Notion field names/types/options are checked before processing. A per-application D1 compare-and-swap lease lasts 120 seconds. An idempotent D1 batch commits event completion and claim release together. All effects require the durable claim, and each provider request has a five-second deadline covering fetch and streamed JSON. JSON is limited to 64 KiB; redirects are rejected with `redirect:manual`; fixed HTTPS provider hosts and API version are compiled into code. Fetch is called without a receiver, compatible with workerd.

Before checking Notion schema, a database compare-and-swap reserves the next probe and increments a saturated failure counter. Cooldowns are 5, 10, 20, 40, 80, 160, 320 minutes, then 24 hours after the eighth failure and each later failure. Concurrent invocations, restarts and uncertain reservation acknowledgements cannot bypass the reservation. A successful schema check resets the budget only if its probe token is still current and unexpired. Missing/invalid credentials, mismatched schema and outages leave events pending without consuming event retries; the daily recovery probe (only while work is due) avoids permanently missing valid work after repair. This is a sustained request-rate budget, not a permanent failure cutoff. Never clear effect UNKNOWN to recover a schema failure.

Notion lookup filters exact External Case ID, allows at most two pages/two matches, and rejects duplicate results, malformed pages/cursors, incomplete pagination, wrong parent, archived/trashed pages, wrong kind/channel/ID, and a conflicting stored link. Every attempt reconciles even a previously linked page. Creation persists UNKNOWN **before** dispatch. Once UNKNOWN, an empty lookup can never authorize creation; only finding and validating the existing page can resolve the ambiguity. Failed linking, provider timeout, oversized/malformed response, redirect or process restart cannot trigger a blind second create. This deliberately favors manual repair over duplicate tickets.

The External Case ID `c3250338-3691-4fae-a7ae-35ed66a31a23` is seeded as a reconcile-only adoption event. It is not treated as a Notion page ID. No match causes bounded retries and eventual blocking, never creation. A validated match records its actual page ID and permanently suppresses retroactive email, whether or not an applicant row is currently present. No other preexisting applications are backfilled for notification.

Membership Decision has exactly Pending, Approved, Declined and Not applicable. The adapter never provisions schema or options. Mappings are pending → Inbox/Pending, approved → Waiting/Approved (invite-ready only), rejected and revoked → Closed/Declined, expired → Closed/Not applicable. Every non-adoption event syncs the latest application status before completion, including delayed submissions. Missing applications or failed PATCHes retain the event for repair. No applicant PII or notes enter Notion or email.

Owner notifications use only Resend, with sender `support@bigsoxstudios.com`, recipient array exactly `[fridman.greg@gmail.com]`, fixed generic subject/body and the fixed protected queue URL. No CC, BCC, reply-to, applicant address, caller-supplied text or other destinations are accepted. The stable provider `Idempotency-Key` is `membership-notify-v1-<application UUID>`. There is no code import from Mail Desk receipts/reply machinery or canary send authorization.

Sending additionally requires exact sender/recipient configuration, a valid key format, a nonzero approved `NOTIFY_START_MS` at or before the current time, an unexpired `PROVIDER_VERIFIED_UNTIL_MS` no more than 24 hours ahead, and `PROVIDER_DAILY_LIMIT` as an integer string 1–10 (default 0). These are deployment attestations, not proof from the provider. A future operator must establish sender/domain authorization, key scope and current shared-account quota/no-spend headroom before setting them. The local limit is an atomic, durable daily attempt reservation across applications, not a shared-account usage monitor. Configure it within verified available daily/monthly shared budget; do not assume ten/day is affordable. A UTC day boundary does not erase attempt uniqueness for an application. The expiring attestation requires deliberate renewal.

Applications older than the explicit cutover are suppressed rather than mailed retroactively. Manual and legacy case suppression is permanent. After validating all email policy gates, the Worker atomically reserves its daily budget and persists email UNKNOWN in one D1 transaction. An intent failure rolls back the reservation and permits safe resumption. A lost commit acknowledgement leaves durable UNKNOWN and cannot authorize dispatch on restart. Once dispatch is possible, timeout, malformed response, redirect, 5xx or acknowledgement-write failure leaves UNKNOWN. Explicit refusal (400/401/403/422/429) records REFUSED. Neither state ever permits automatic resending, even after provider idempotency windows expire. Resend reconciliation/manual owner action remains necessary; this Worker does not infer delivery from a response timeout or automatically reset a claim.

Safe reads and idempotent decision assignment use bounded backoff (5, 10, 20, 40, then 60 minutes) and block after eight failures. Disabled email, missing/expired attestation and exhausted daily quota leave email NEW and the event pending without consuming failure attempts. A one-hour deferral rotates these waits behind other due work, including expiration closure; they resume automatically once verified gates and quota permit. Cutover suppression applies only to a valid, nonzero cutover. UNKNOWN/REFUSED still require manual provider review and never retry automatically. A crash can leave a lease until expiry; durable effect intent remains independently authoritative. Logs include only a fixed event label and one fixed failure category: configuration, notion_read, notion_unknown, notion_conflict, notion_update, resend_unknown, resend_refused or storage. Never log provider responses, exceptions, headers, credentials or applicant content.

## Exact privacy and retention

Applicant lifecycle after this correction:

- Pending applications expire at 90 days, in bounded batches of 100, with actual closure time starting the clearing interval.
- Name, email, answer and owner note clear 30 days after rejection, withdrawal/revocation or expiration, in batches of 100. Notification failure never delays clearing.
- Approved/invite-ready requests and their personal details remain until explicit invitation, withdrawal or manual closure. Annual owner review only: age 365 days is a review flag, never automatic expiration, PII clearing or deletion. The owner records an annual review note and retains approval, or explicitly withdraws approval to close an invited/otherwise closed request. Invitation/account actions require their separate authorized process; saving a review never performs them.
- Deidentified audit events expire at 365 days (12-month convention), in batches of 500. Existing minimal UUID/status/revision/email-HMAC tombstones remain to prevent duplicate applications/reopening. The fingerprint is pseudonymous.

Annual review uses existing `created_at` metadata: `annual_review_due_at = created_at + 31536000000` (365 days). The private owner queue displays “Annual owner review due” for approved requests at that boundary, including older paginated records; the flag stays visible until explicit closure. A note-only annual review increments the revision/audit but does not change status, reset the age flag, or enqueue a notification. There is no additional periodic review requirement or automatic action. Once per year the owner should review **all** approved requests, retaining those still invite-ready, and record the review date/decision in the private owner note. To avoid missing older pages, an authorized operator can produce this minimal private report with an explicit millisecond review time bound as `?` (SQL recipe only; no live query executed here):

```sql
SELECT id, created_at, created_at + 31536000000 AS annual_review_due_at,
       CASE WHEN created_at + 31536000000 <= ? THEN 1 ELSE 0 END AS annual_review_due
FROM membership_requests WHERE status = 'approved'
ORDER BY created_at, id;
```

The report contains no applicant text. Review notes remain personal data and clear 30 days after explicit terminal closure. Pending-only expiration emits `expired` → Notion Closed / Not applicable; approved remains Waiting / Approved; explicit withdrawal uses `revoked` → Closed / Declined. These are application decisions, not account access changes. Annual review creates no status event and sends no mail.

Notification outbox events add no applicant text. Completed events expire at 365 days; unresolved/blocked events remain for owner repair. Minimal case links/intent/suppression and send-attempt reservations are retained as pseudonymous side-effect tombstones, independent of audit/event pruning, so retention cannot cause another create/email. They are not email content or delivery receipts. This run adds no provider retention promise: the minimal Notion page and fixed email are subject to their existing provider retention and owner administration. Database backups and verified removals retain the existing operator obligations; never restore stale PII or forget provider-effect suppression when restoring.

## CPU and remaining enablement gates

One event per invocation bounds JavaScript/provider work (up to six provider requests including two query pages). Provider/D1 I/O is awaited, with no polling, hashing or expensive crypto loop; crypto work is limited to UUID probe/lease tokens. Provider JSON remains bounded at 64 KiB. Completed-event pruning is bounded at 100, uses the covering state/age/ID index without a temporary sort, and runs even when disabled; unresolved events are never TTL-pruned. Empty disabled runs execute only the indexed bounded delete; enabled idle runs make no provider requests. Schema failures use the persistent backoff above rather than polling every cron tick. Safe failures block after eight attempts for explicit repair; policy/quota waits remain resumable. At a five-minute schedule the theoretical drain ceiling is 288 events/day, lower with waits/failures; actual backlog and shared free quotas must be checked before activation.

A bounded batch is not proof of <10 ms CPU on production Free Workers. Local workerd correctness tests and dry runs do not provide production CPU percentiles or shared-account quota evidence. Production CPU headroom below 10 ms and current strict-$0 shared provider/resource capacity remain enablement blockers. Keep all flags false and limit 0 until separately authorized verification resolves them. No production/provider access is authorized by these corrections.

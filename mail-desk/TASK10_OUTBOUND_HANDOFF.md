## Implemented offline

### Additive immutable storage

`migrations/0004_outbound_approval.sql` adds `outbound_provenance` and `live_outbound_reviews`; 0001–0003 remain byte-for-byte unchanged. There is **no backfill**, including no guessed receipt/message associations or authentication of historical mail.

Evidence is linked by FK to a receipt and inbound message and checked against the existing receipt/message mapping and same case. Evidence, receipt source, mapping source, and inbound message source become immutable once evidence is captured. Deletes of evidence/reviews/mappings are denied; receipt/message FKs preserve their source rows. This requires the existing foreign-key enforcement. Evidence insertion requires completed forwarding, so normal forwarding state transitions are not frozen mid-flight. The current inbound Worker never inserts evidence.

Each live review has a durable UUID intent/idempotency key, case/revision/session/expiry/purpose, receipt/message linkage, and one immutable JSON snapshot. That snapshot includes actual envelope, claim token, forwarding state and receipt/message timestamps, inbound message body, signed provenance/policy, parsed Message-ID/In-Reply-To/ordered References, exact proposed sender/recipient, subject/body, revision and session. Ten-minute expiry is checked in code and constrained in SQL. Unique `(case_id,revision)` prevents replacement of an approval at the same revision. SQL triggers allow only `reserved -> approved -> dispatching -> sent|failed|UNKNOWN`, with no terminal reset or deletion. UNKNOWN is never retried, including after provider idempotency expiration. Cross-table triggers prevent mock/live claims on the same revision and block conflicting dispatching/UNKNOWN attempts and draft/revision edits.

A populated synthetic 0003 upgrade test preserves cases, inbound/outbound messages, forwarding receipts/mappings, mock intents, jobs, dedupe, audit, Notion links/activity/backoff, and checks FKs. An old mock Worker still works with additive 0004. No migration has been applied to any deployed database.

### Recipient and thread eligibility

`src/outbound.provenance.mjs` chooses the latest inbound message server-side; it never accepts a receipt, recipient, From, Reply-To, thread or approval boolean from the browser. Latest-time ties, missing mappings/evidence, synthetic intake, non-support cases, cross-case mappings, unforwarded receipts, cutoff equality, mismatched requester/envelope, ambiguous Message-IDs and unverifiable ancestors fail closed. A later unverified inbound message blocks fallback to an older verified message.

The future evidence contract uses lossless ordered header pairs, not `Headers.get()` output. The deliberately conservative parser rejects duplicate names, folding/control characters, malformed IDs, multiple IDs, mismatched From/To/Reply-To, duplicate/oversized References, self-reference and conflicting parent order. Unsupported display-name/quoted/encoded mailbox headers are denied rather than silently repaired. Accepted From/Reply-To syntax is only a consistency check; it does **not** authenticate a sender.

A parent becomes outbound In-Reply-To; bounded verified ancestors followed by that parent become References. Every selected ancestor needs its own signed evidence, same case, exact sender/studio envelope, post-cutoff timestamps, mapped inbound message and completed forwarding. Generic support reply threads remain supported in offline tests. The existing inbound and Notion thread code is unchanged.

### Separate coordinator and runtime block

`src/worker.outbound.mjs` is a separate future HTTP entrypoint. No config, hostname, email handler, scheduler or asset binding was added for it. It does not replace the active staging entrypoint. `src/outbound.candidate.mjs` implements the isolated coordinator:

- Exact-owner signed Access JWT verification, plus a signed `amr` containing `mfa`; absence fails closed. This is a candidate requirement, **not proof that deployed Access emits this claim or enforces the correct policy**.
- Origin, same-origin metadata, authenticated session cookie, CSRF and rate limit. A distinct `LIVE_APPROVAL_SECRET` must differ from the mock/session `CSRF_SECRET`.
- Purpose `maildesk-live-review-v2`. A review HMAC covers the complete immutable snapshot/linkage/session/expiry. Explicit `/approve` consumes the review phase and returns a different send-phase HMAC. A review token cannot send. Approve replay, changed tokens, other sessions/cases and expiration are denied.
- Server-only eligibility and exact snapshot reload before approve/send. Atomic D1 UPDATE checks current revision/body/subject/requester/channel/latest inbound and conflicts again at the write boundary; source provenance is frozen in SQL. One invocation wins before the private transport closure is called. No serializable `humanApproved` value grants transport authority.
- First-canary restriction: only support@, exactly one sender allowlist entry and exactly one recipient entry equal to the exact owner mailbox. Customer recipients, members@ and hello@ cannot use this candidate.
- Transactional accepted-message/outcome audit finalization with provider ID retained in the durable review. No existing Notion jobs are consumed/changed. `sent` here means **provider acceptance, not inbox delivery**. Any persistence failure leaves dispatching for private reconciliation, never another request. Recovery only advances stale dispatching to UNKNOWN.

The production factory always refuses mutating routes with `verified_ingress_unavailable` (or an earlier security/gate/schema denial). Its verifier returns false and its transport throws. Neither environment flags nor a provider argument can change that. The owner-only session endpoint reports `liveAvailable:false` and `live pending: verified ingress unavailable`; there is no live-send UI. The existing Mail Desk UI remains truthfully mock-only.

Only `createOfflineOutbound` exercises these routes. It requires an explicit local provider stub, ephemeral public Ed25519 fixture key, `.test` application/owner, literal `offline-placeholder` credential, and an owner-canary allowlist. Ed25519 verifies fixture evidence bytes; **fixture assertions are not real DMARC evidence**. The fixture private key exists only in the test process. Never wire this factory to HTTP deployment, pass global fetch, or treat it as a production policy implementation.

### Resend wire candidate

`src/resend.future.mjs` retains its unconditional live bridge block. The offline coordinator calls the existing private wire through the restricted rehearsal, after its D1 claim. Body validation now also rejects hidden control bytes. Staging still cannot import or select this transport, including through malicious provider injection or production flags.

Wire behavior: fixed `https://api.resend.com/emails`, POST, manual redirects, one mailbox, plain text, strict subject/body/thread validation and exact allowlists; no arbitrary custom headers, HTML, CC or BCC. ## Blocking provenance policy: further implementation required

The current receipt schema persists normalized envelope/thread hints, but neither authenticated ingress event evidence nor a lossless raw header set. A successful forward is insufficient proof of DMARC, exact mailbox ownership, header integrity or the absence of duplicate original headers. Cloudflare's [authentication requirements](https://developers.cloudflare.com/changelog/post/2025-06-30-mail-authentication/) do not turn these old records into per-message proof. Do not backfill a pass flag from forwarding success, raw Authentication-Results, From, Reply-To or an owner button.

Before any real-send path exists, independently implement and review an ingress verifier outside the browser and send Worker. Its signing key must not be held by either. It must authenticate the ingress event source, retain a bounded lossless header set and verify message integrity, reject spoofed/ambiguous auth-result traces, and validate usable aligned authentication at receipt time. DMARC authenticates domain alignment, not possession of an exact local-part mailbox. The contract's `authenticatedMailbox` therefore requires a separately reviewed exact-mailbox ownership/challenge policy, initially for the owner canary. A real verifier must not simply copy envelope From into it.

The current contract (`maildesk-ingress-v1`) signs exact serialized evidence bytes and binds receipt key, case/message association, actual envelope, receipt/message timestamps, policy and unique verifier event, plus raw headers and verified authentication/header-integrity/mailbox facts. Review freshness, event replay prevention, authenticated domain/signature coverage, challenge lifecycle, key rotation/revocation and storage privacy before adopting this contract. The current schema retains signed assertions; a production evidence design may require additional fields/migration to retain independently auditable verification details. No HTTP evidence-write route or production verifier key/configuration is present.

A future production implementation must pin verifier public keys in reviewed code/config, enforce the complete evidence policy, then connect the private claimed-intent transport to the wire. Do not remove the runtime block or replace it with an env boolean, user-supplied callback or mock HMAC. Re-test all concurrency/security cases through that actual production graph. Confirm the Access MFA claim contract against signed deployed tokens and owner policy; if unavailable, keep blocked and design another verifiable enforcement mechanism. Tests with synthetic JWTs do not prove deployed MFA.

The separate production UI still needs a full frozen envelope/body/thread/provenance review with truthful draft/review/approve/provider-accepted/UNKNOWN labels. Sending must remain unavailable until all of the above is reviewed. Lost approval responses must never reset an approved intent; current behavior favors fail-closed recovery over automatic reissue. Outbound provider ID is retained, but RFC outbound Message-ID and cross-direction threading/reconciliation require separately reviewed provider metadata integration; never guess Message-ID from the provider UUID. No live Notion outbound activity integration was added.

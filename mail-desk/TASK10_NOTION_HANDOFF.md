## Implemented behavior

`src/notion.live.mjs` is separate from the unchanged offline mock. Every request requires exact `NOTION_SYNC_MODE=live`, exact `DEPLOYMENT_STAGE=staging`, a nonblank `NOTION_API_TOKEN`, a present valid `NOTION_SYNC_START_UNIX`, and exact case channel `support`. The cutoff is a decimal digit string of Unix **seconds** >= 0, representable as a JavaScript safe integer (maximum 9007199254740991); signs, whitespace, fractions, exponent notation, nonstrings and unsafe integers fail closed. Missing/malformed cutoff returns OFF before D1 or network. Zero is used only in synthetic test fixtures; it is not an activation default. The fixed host is `https://api.notion.com`; API version is `2025-09-03`. Only module-owned page-create and the two source-query paths are accepted. POSTs use manual redirects, reject redirects and non-success responses, enforce a nine-second deadline over transport and body reading, and bound streamed JSON to 256 KiB. Errors are fixed codes; no console logging, raw responses, secrets, email addresses or bodies are emitted. The token is used only in the Authorization header. Unit tests inject fetch and cannot access either service.

Only these existing sources are used:

| Purpose | Existing source | Query key |
| --- | --- | --- |
| Studio Backlog & Tickets | `103d8328-de8b-4b7f-8986-000ce40450b5` | External Case ID, rich_text equals case UUID |
| Studio Ticket Activity | `17401fd3-c5f4-46bb-b516-c420b6e3ce24` | Event, title equals `Inbound email <message UUID>` |

No databases or views are created. The new ticket mapper uses the owner-verified select/rich_text/email schema: Service Management, Incident / Support, Inbox, support@, requester name/email, External Case ID, Not applicable, Needs approval, Greg, Normal, Other. It is used only for a new page with a data_source_id parent. There are no PATCH requests. Existing tickets, including closed tickets, keep their entire workflow, Status, Assigned To, Reply State, Reference and Notion Sequence. Other Studio Work records are never queried broadly or edited. The existing Reference allocator and five-minute automation are unchanged.

`src/notion.sync.mjs` queries before creation and stores claims in `notion_links` or `notion_activity_links`. Unique case/message keys select one creator across concurrent invocations sharing the same D1. Before the external POST, `creating` advances durably to `UNKNOWN`. Success links the returned page. A timeout, exception, API 400/429/500, redirect, malformed response or local persistence failure leaves a durable suppression record. **A create is never automatically retried**, including on a definite rejection. Subsequent work queries the stable key for reconciliation. Missing results after any prior claim/link cannot authorize a create. Multiple matches, incomplete pagination or a conflicting stored page ID refuse work. Queries retrieve at most two matches over at most two pages; beyond that they fail closed. Existing Activity matches must have exactly the expected Event title and relate to exactly the expected ticket without truncated relations, otherwise reconciliation refuses them.

The Worker now binds `scheduled(controller, env, ctx)` to `ctx.waitUntil(runNotionSync(...))`. There is no HTTP trigger. Without all live/staging/token/cutoff gates it touches neither D1 nor network. With authorization configured it selects at most five eligible cases and attempts at most five inbound activities across an invocation. Cases require exact support channel and a receipt forwarded to `support@bigsoxstudios.com`; any synthetic `inbound_dedupe` case is excluded. The forwarded receipt must have `created_at > NOTION_SYNC_START_UNIX`, not merely a later forwarding/update timestamp. Activities additionally require both receipt and message `created_at` strictly greater than the same cutoff, plus the exact receipt-to-message association, matching case, forwarded state and inbound direction. Mock outbound `delivery_sent` jobs/messages never qualify. The live queue uses durable links rather than modifying `sync_jobs`; historical mock jobs stay unchanged, including on failure or success. Its aggregate result distinguishes complete, partial and unavailable work; scheduled results are not currently exposed in the UI.

Additive `0003_notion_activity.sql` creates `email_receipt_messages` and `notion_activity_links` (message UUID primary key and FK, case FK, unique page ID, creating/linked/UNKNOWN state, update timestamp). It also adds `notion_sync_backoff` (case FK and timestamp only) to pace read failures without creating a side-effect suppression claim. No prior columns or data change. Inbound intake optionally detects the new mapping table and records receipt/message linkage in the same atomic batch as intake. Without 0003, accepted 0002 behavior continues. No Notion call is made during intake, so forwarding is independent of sync. Every newly tracked forwarded inbound email/reply can produce one generic Work Note activity, with Author System, a stable UUID Event title and Ticket relation. Details contain a fixed instruction to review the original in the owner inbox, never message content or customer identity.

## Safety limits and deferred gaps

- Exactly-once creation is a safety target, not guaranteed delivery: uncertainty can permanently leave zero visible pages. The code favors no duplicate over automatic recovery. Never delete/reset claims, receipt keys or suppression records to force a retry. A crash before POST can also leave creating/UNKNOWN. Owner investigation is required if later queries remain empty.
- **Future mail only by default.** Existing real support mail and historical self-sent TEST canaries are excluded by the activation cutoff. Never lower/reset the cutoff to import them without separately reviewed consent. A new forwarded reply after cutoff may safely create a ticket for an older case using its existing case identity/metadata; only qualifying post-cutoff messages produce activities. Exactly-at-cutoff receipts/messages are excluded conservatively because intake timestamps have one-second resolution. Email Date headers, case timestamps and receipt updated_at cannot bypass the cutoff.
- Historical receipts lack a reliable local message UUID association. 0003 deliberately does not infer one from timestamps, order or Message-ID. Even with separately reviewed backfill consent, historical activities would need an explicitly reviewed association; this implementation has no backfill or repair UI. New mail received while a prior Worker is running also lacks this mapping, so coordinate the reviewed rollout before choosing the activation cutoff.
- Notion has no unique constraint or transaction spanning D1 and page creation. The D1 claim prevents duplicate creates by this implementation sharing one D1, not independently running external writers. The owner must ensure no other service creates the same External Case ID or stable Event title. Preserve the existing allocator/service and coordinate ownership of these new activity titles; this app does not emit a separate Created activity.
- The bounded scheduler prioritizes unlinked eligible cases, then linked cases with due activities, then unresolved ticket claims. Unresolved creating/UNKNOWN tickets and activities wait one hour using their link updated_at before **read-only reconciliation**, with timestamps refreshed before reading. An invisible previously linked ticket becomes UNKNOWN while preserving its page ID. Query errors/conflicts before a claim use additive case-level `notion_sync_backoff`; failed activity reads also defer that case for one hour. Backoff expiry only authorizes a new read, never another ambiguous create. During case-level backoff a fresh reply on that same case may also wait up to an hour; other new cases keep progressing. Priority is not a general fairness guarantee under sustained overload. There is no paid queue, dead-letter dashboard, alerts, live outbound sync, workflow patch, automatic UNKNOWN reset or resend path. Run bounded supervised canaries first.
- Local SQLite proves migration/claim behavior locally, not actual D1 consistency, Worker CPU/concurrency, deployed network timeout/cancellation, Notion permissions/eventual consistency, forwarding delivery or owner Access/MFA. No real schema/permission/runtime acceptance is claimed. HTTP UI/session remains the historical staging UI and reports Notion off; it is not a sync monitoring surface.

## What Cloudflare evidence establishes

Public documentation was read on 2026-10-16 for design context, never runtime assurance:

- The [Email Worker runtime API](https://developers.cloudflare.com/email-service/api/route-emails/email-handler/) exposes SMTP envelope addresses, a raw MIME stream and a `Headers` object. An actual provider invocation supplies transport context to that handler. Raw bytes preserve inspectable message structure, not sender identity. Normalized headers cannot serve as lossless original evidence. The documented interface does not expose a signed authentication verdict tied to a receipt and content hashes; our existing database stores no such authenticated per-event status. Documentation alone cannot prove the provenance of an object supplied to a handler. Its `reply()` DMARC guard is an action restriction, not an exportable, stored attestation for this outbound path. No reply was attempted.
- Cloudflare's [June 30, 2025 authentication announcement](https://developers.cloudflare.com/changelog/post/2025-06-30-mail-authentication/) requires SPF **or** DKIM for forwarding beginning July 3, 2025, and separately recommends DMARC. Forwarding success therefore cannot be upgraded into per-message aligned DMARC, original-header integrity, or exact local-part mailbox possession. This is a policy inference from the published requirement, not a claim about an undocumented internal verdict.
- [DMARC, RFC 7489 §§2.2, 3.1](https://www.rfc-editor.org/rfc/rfc7489.html#section-3.1) concerns domain identifiers/alignment. A domain pass does not authenticate the exact local-part mailbox. SPF needs original SMTP connection facts; rechecking a forwarded message using the forwarder's IP is insufficient. DKIM needs signature/coverage and original-byte verification, not the presence of a DKIM-Signature field. A separately verified exact-mailbox challenge is required by this candidate's stricter policy.
- [Authentication-Results, RFC 8601 §§5, 7.1](https://www.rfc-editor.org/rfc/rfc8601.html#section-7.1) requires an established trust boundary. A forged `Authentication-Results` or `Received` field is never proof. Matching an `authserv-id` string to Cloudflare is insufficient. Neither an owner approval boolean nor a forwarding receipt closes that boundary.

We have not identified or integrated an authenticated Cloudflare per-event verification feed suitable for this contract. Do not infer its existence from these docs or their examples. A credible external verifier must independently obtain trusted ingress facts, not sign fields reported by the exposed receive/HTTP/send Worker. Signing arbitrary email assertions makes them attributable to a key, not true.

## Implemented contract and exact limits

`offline/ingress.policy.mjs` is a bounded **contract validator with cryptographic fixture verification**, not a provider authentication implementation. No `src/` module imports it. It has no fetch, endpoint, database writer, provider transport, credentials, private key, real public key or production constructor. Both configured mailboxes and both issuer origins must use `.test`; mode and purposes are explicitly offline. The only acceptance result is `{kind:'offline-policy-accepted-not-authority', eventId}`. It cannot be inserted as `maildesk-ingress-v1` evidence. Do not adapt its output to the old v1 fields.

`test/ingress.fixture.mjs` only loads in Node's test runner, generates separate nonextractable ephemeral ingress/challenge private keys, never exports them, and refuses real mailbox/issuer identities. It deliberately permits malformed policy assertions for adversarial tests. `.test` checks are guardrails; they are not proof a signer verified a provider. The tests explicitly demonstrate that a signer can lie and still pass structural/signature checks. The module is unsuitable for live use even with convincing claim names.

| Boundary | Rehearsal policy |
| --- | --- |
| Signed bytes | Exact UTF-8 `JSON.stringify` payload string, maximum 65,536 bytes. Parse/reserialize equality rejects duplicate JSON members and alternative encodings. Exact schemas reject extra claims, including user approval, ownership shortcuts and embedded keys. Signatures cover every claim, including purpose/algorithm/issuer/key ID. |
| Algorithms and anchors | Only Ed25519 with pinned 32-byte public keys and canonical unpadded base64url 64-byte signatures. One explicit issuer/key ID/role/validity interval per producer, separate keys and origins. No evidence-provided JWK, URL, algorithm negotiation or verifier callback. |
| Binding | Exact receipt, case, internal message ID, envelope and receipt/message timestamps against separate expected fixture records. UUID-like IDs are bounded opaque identifiers, distinct from the raw RFC Message-ID. Owner and destination match exactly; no address normalization, aliases, plus removal or inferred mailbox ownership. |
| Header representation | Parse raw bytes directly, bounded to 128 KiB total, 32 KiB headers including `CRLFCRLF`, 96 KiB body, 100 lines, 4,096 characters/line. Preserve original ordered name/value pairs, including case and all spaces after the colon. Reject every duplicate name case-insensitively, folds, bare newline, controls, non-ASCII and malformed names. This intentionally rejects valid complex MIME, including repeated Received fields; it never repairs ambiguity. |
| Hashes | SHA256 of exact header bytes **including** the terminating `CRLFCRLF`, and exact remaining body bytes. No decoding, trimming, newline conversion or MIME reserialization. Reparse pairs from the same raw snapshot and require exact signed-pair equality. These are integrity bindings, not DKIM verification or proof of who supplied bytes. |
| Header consistency | Single bare From/To, optional identical Reply-To, narrow `.test` RFC Message-ID. Unsupported addresses/threads remain denied or subject to the existing separate thread policy; this prototype does not grant thread authority. Authentication-Results/Received values never affect authentication decisions. |
| Authentication assertion | Independently signed fixture producer claim, fixed source label and evidence reference, DMARC pass with SPF or DKIM and exact domain equality with From. This is a conservative strict-alignment subset; no relaxed alignment, PSL guess, ARC exception, fake SPF evaluation or header-derived verdict. The label/reference is not proof of an actual provider check. |
| Standalone challenge | Separately pinned issuer/key/purpose verifies exact owner mailbox, challenge ID and SHA256 of the **entire ingress payload**, binding all event/content/linkage claims. Verification must follow ingress issuance and expire within 600 seconds. No approval boolean or ingress-signer ownership assertion can replace this second signature. No challenge email is generated or sent. |
| Time | Explicit positive cutoff, receipt/message and challenge strictly after cutoff; ordered receipt ≤ message ≤ issuance ≤ now, receipt age ≤300 seconds, attestation expiry ≤300 seconds after issuance. No future clock tolerance or historic backfill. Key intervals checked at validation and event/proof times. |
| Replay | After all checks, synchronously reserve event, receipt, message and challenge IDs with one winner across concurrent promises. No await in the final check/reserve step. Maximum 10,000 successes per policy instance, then deny; invalid attempts do not consume IDs. This is **process-local only**, deliberately not a durable replay service. Restart/reconstruction clears it, so it cannot support production acceptance. |

Constructor configuration and per-request bytes/claims/expected records are snapshotted before asynchronous verification. Expected records and the clock are fixture inputs; in any future implementation they must originate from an independently trusted registrar and authoritative persisted records, never request JSON. Public-key signature authenticity cannot establish that those inputs or signer assertions are truthful.

## Future integration contract — blocked, not implemented

1. **Independent ingress truth:** choose and audit an upstream SMTP receiver or authenticated provider event source with authenticated original connection/envelope context, complete original bytes, immutable event IDs and verifiable authentication details at receipt time. Specify source authentication, event retrieval/integrity, replay protection, DNS/key timing, DKIM signature/header/body coverage (including duplicate and `l=` risks), SPF identity/source-IP evaluation, and aligned DMARC. If that source cannot be obtained, keep blocked. An external service signing an exposed Worker's self-reported claims is insufficient. Recomputing DKIM may be possible from original bytes and appropriate DNS evidence; SPF cannot be reconstructed from arbitrary Received headers.
2. **Signer placement:** a trusted producer outside **all exposed receive/HTTP/send Workers** validates that source before signing. Its signing key must never be in those Workers or the browser. Authenticate any internal transport and independently audit the verification implementation. The mailbox challenge service uses a separate key, principal and verifier. These services cannot accept browser flags as facts. Public verification keys alone convey no signing authority. No production signer/key is supplied here.
3. **Exact mailbox proof:** independently register the exact owner address and deliver a high-entropy, purpose-bound, expiring standalone challenge through a separately reviewed channel. A verifier authenticates completion, rate limits attempts, stores only token digests, prevents reuse, binds proof to the ingress digest and records completion/expiry/revocation. A receipt of forwarded mail, login email equality or owner click is insufficient. Challenge completion demonstrates mailbox access at that time; it does not prove authorship, legal identity or absence of account compromise. No live challenge flow is authorized here.
4. **Authoritative linkage and storage:** a trusted registrar assigns or validates receipt/case/internal-message linkage against the independently authenticated event, exact envelope, content hashes and timestamps. Never let the exposed Worker persuade a signer to bless arbitrary mappings. A private ingestion process independently verifies both signatures, pinned capabilities, current revocations, cutoff, local bytes/mapping and challenge proof before storing provenance. In one durable atomic transaction enforce unique issuer/event, receipt, internal message and challenge tombstones and immutable mapping/content. Persistence conflicts, partitions, time uncertainty or exhausted capacity deny acceptance. Do not mark accepted before commit. No event evidence-write HTTP route is implemented.
5. **Schema/version:** the frozen 0004 table accepts only `maildesk-ingress-v1` and cannot safely encode this rehearsal as live evidence. A separately reviewed additive schema and live policy version would need canonical signed ingress/proof bytes, signatures, issuer/key/policy IDs, independent evidence references, exact content digests, linkage, revocation and permanent replay tombstones. Never change 0001–0004 or backfill old inbound messages. Set a new approved future cutoff before ingress integration; equality and all historical records remain ineligible. A later unverified inbound still blocks fallback to an older verified one.
6. **Privacy:** minimize retained raw content and header data; headers may expose addresses, IPs and internal topology. Treat hashes as sensitive/linkable, not anonymization. Approve access control, encryption, retention and deletion policy before storing anything. Keep necessary immutable evidence/replay audit records under a reviewed retention policy; avoid logging bodies, challenges, credentials or raw tokens. Use encrypted restricted evidence storage with digest references where appropriate, and verify retrieved bytes. No real data was captured for this milestone.
7. **Rotation and failure:** approve pinned issuers, role-separated key IDs, validity windows, overlap and revocation distribution out of band. Reject unknown IDs, expired/revoked keys and unavailable revocation/source/challenge verification. Never fetch trust anchors from a message. Rotation must not reset event/challenge uniqueness. Revalidate provenance and revocation before review/approve/send; immutable old signatures alone do not authorize a future send. Clock/source outages fail closed without guessing or retries that grant new send authority. The offline constructor is a static snapshot, not a rotation/revocation service.
8. **Access MFA:** independently validate deployed Access issuer/audience/signature/time, exact owner principal, and an authenticated MFA assurance contract/policy using separately authorized deployed acceptance work. Existing synthetic `amr:['mfa']` tests prove only candidate behavior. If deployed tokens do not provide adequate signed assurance, retain the block and design a verifiable enforcement alternative. Access login or MFA cannot substitute for ingress authentication or exact-mailbox proof. Keep Origin/session/CSRF and explicit immutable review/approve/send phases.
9. **Release/rollback:** independent manual security review, populated migration rehearsal, durable multi-instance replay/concurrency tests and separately authorized configuration/deployment/canary are still needed. Never enable this `.test` constructor in a Worker. Retain the unconditional production block until a distinct reviewed implementation exists. Rollback disables future evidence acceptance and sending first, revokes affected signer/provider credentials if appropriate, and preserves immutable evidence, replay tombstones and uncertain outcomes; it must leave current forwarding and five-minute Notion sync intact. Nothing here grants approval to perform those operations.

# Security boundaries

Task 10 supplement: [offline handoff, reconciliation and activation gates](TASK10_HANDOFF.md). Inbound remains disabled (enable flag absent from staging); live Notion and send remain unwired. This supplement supersedes historical Task 9 statements about the absence of an email handler.

Every route, including `/`, scripts, styles, unsupported methods and unknown paths, authenticates `Cf-Access-Jwt-Assertion` before data access. Cloudflare Access is an additional perimeter, never a replacement for local verification. The sole owner email must exactly match the configured value. No fallback token headers, Access cookie verification shortcut, email-header trust, CORS wildcard, public API or unauthenticated health endpoint exists.

The signed `__Host-maildesk` nonce cookie has Secure, HttpOnly, SameSite=Strict and Path=/ with no Domain. Its HMAC binds to a SHA-256 digest of the verified JWT. GET `/api/session` issues the corresponding CSRF proof. POST requires this cookie and an HMAC CSRF header, exact configured HTTPS Origin, and no cross-site fetch metadata. A changed JWT invalidates both CSRF and review approvals; refresh the session and review again. Cookie lifetime is one hour; the JWT's checked expiry remains the server authorization boundary. CSRF_SECRET must be a random independent secret of at least 32 characters, provisioned only during future authorized configuration.

POST JSON is bounded to 20,000 UTF-8 bytes while streaming; supplied Content-Length must agree. Text drafts are bounded to 10,000 characters. Field allowlists reject every To, From, recipient, sender, CC, BCC or HTML override, including values that happen to match. Revision numbers are integers. Each owner is limited by an atomic D1 upsert to 30 POST requests per 60-second window, including rejected application actions after CSRF validation. Denied authenticated actions log only controlled error codes. Unauthenticated attacks are not written to D1 to avoid a public write/amplification path.

The server derives the receiver from the case's requester email and the sender from its fixed channel. Review captures an immutable snapshot in a UUID intent with a ten-minute approval HMAC binding **case + revision + receiver + sender + subject + body + authenticated cookie/JWT session + expiry + intent UUID**. GET and Review never dispatch. Final Send requires that approval and atomically verifies the current revision. Draft edits invalidate previous approvals. Reviews are unique per case revision; expired or session-changed reserved reviews require saving/reviewing a fresh revision. Client controls are convenience only; the API enforces these boundaries.

The only imported send provider is the mock. Its `sent` result denotes simulated success, never mail delivery. `SEND_MODE=live`, missing mode, or disabled mode is denied even when production flags or a synthetic API key are injected. The unimported future adapter must pass separate production/live/allow/secret gates and must never be wired into this staging artifact.

A dispatch is claimed before provider invocation. The claim cannot be reset by any API or sync job. A definite rejection becomes `failed`; timeout, thrown error or ambiguous result becomes `UNKNOWN`. Both are terminal for the intent. UNKNOWN or dispatching blocks new drafts and sends for the entire case. Finalization failure leaves dispatching and returns a generic 503. An offline recovery helper can turn stale dispatching into UNKNOWN, never reserved. Provider timeouts do not prove cancellation; they deliberately lock the case. There is no resend/reconcile HTTP endpoint.

Audit records do not contain bodies, requester PII, JWTs, CSRF proofs, approval tokens or provider error strings. D1 contains private requester data and draft/reply text. It must never be connected to public analytics or exposed through static assets. The remote studio logo is allowed only from the provided brand host with no referrer; all other scripts, styles and connections are same-origin. No third-party JavaScript or rich email rendering exists.

No custom MFA configuration is claimed by this application. An independent Access application and the owner's required custom MFA must be created and reviewed outside this coding task before any staged UI is accepted. Verify that real Access assertions supply all mandatory temporal claims; otherwise requests intentionally fail closed. Browser testing of cookie/Access interaction remains required.
